---
title: Relations & Eager Loading
description: Load related rows with Include() and avoid N+1 queries
---

`Include()` loads related rows with extra queries, run after the main one. This avoids the N+1 problem of querying related rows in a loop.

<Warning>
  Without `Include()`, relations are **not** loaded. You ask for them explicitly.
</Warning>

<Note>
  `Include()` works with **has-many** relations, the ones declared with `via` (for example `orders: [Order] via user_id`). Including a belongs-to relation such as `author: User` fails with a missing-foreign-key error. To get the parent of a row, query the parent entity directly.
</Note>

## Include

```go
result, err := eng.Query("User").
    Select("id", "name").
    Include("orders").
    Execute(ctx)
```

```sql
-- 1. main query
SELECT "id", "name"
FROM "users"

-- 2. eager query: one per included relation
SELECT "id", "total", "status", "created_at", "user_id"
FROM "orders"
WHERE "user_id" = ANY($1)   -- $1 = ids from the main query
```

The eager query binds all parent ids as one array parameter. Keep `"id"` in `Select()`, because those ids are what the eager query uses.

### Why separate queries

Eager loading uses separate queries instead of JOINs, so parent rows are not repeated once per child and each row appears once.

## Nested includes

```go
result, err := eng.Query("User").
    Include("orders.items").
    Execute(ctx)
```

This issues one query per level: users, then their orders, then the items of those orders. Including `orders.items` also loads `orders`, so listing both is optional.

## Reading the result

`QueryResult` has:

- `Rows` - The main rows
- `Relations` - Eager-loaded rows, keyed by the relation path (`"orders"`, `"orders.items"`) and also by its last segment (`"items"`) when that name is free

<Warning>
  `Relations["orders"]` is a **flat list** of every loaded order, not grouped by user. Match children to parents with the foreign key field.
</Warning>

```go
result, err := eng.Query("User").
    Select("id", "name").
    Include("orders").
    Execute(ctx)
if err != nil {
    return err
}

ordersByUser := map[string][]engine.Row{}
for _, order := range result.Relations["orders"] {
    userID := fmt.Sprint(order["user_id"])
    ordersByUser[userID] = append(ordersByUser[userID], order)
}

for _, user := range result.Rows {
    id := fmt.Sprint(user["id"])
    fmt.Printf("%s: %d orders\n", user["name"], len(ordersByUser[id]))
}
```

<Note>
  ID values can come back as strings or as byte arrays depending on the column type, which is why `fmt.Sprint` is used above. Prefer one consistent conversion in your application.
</Note>

## IdentityMap

Rows that share the same `id` within one result are collapsed to a single row object. If the same parent or child row appears more than once in the rows the database returns, all occurrences point to the same map. It is on by default and needs no configuration.

It does not change what is sent to the database; it only avoids keeping duplicate row objects in memory for that result.

## Filter on a related entity

`Filter("orders.total", "gt", 100)` selects the **users** that have a matching order; it uses a JOIN with `DISTINCT`. It is separate from `Include()`: the filter chooses the users, and `Include("orders")` loads **all** of their orders. See [Filtering](/queries/filtering#filter-on-a-related-entity).

## N+1

```go
// 1 + N queries
users, _ := eng.Query("User").Select("id", "name").Execute(ctx)
for _, user := range users.Rows {
    eng.Query("Order").Filter("user_id", "eq", user["id"]).Execute(ctx)
}

// 2 queries
users, _ = eng.Query("User").Select("id", "name").Include("orders").Execute(ctx)
```

## Seeing the eager SQL

`.Debug()` prints the main query only. To read the eager queries:

```go
generated, err := eng.Query("User").Include("orders.items").ToSQL()
for _, eager := range generated.EagerQueries {
    fmt.Println(eager[0]) // "orders", "orders.items"
    fmt.Println(eager[1]) // SQL
}
```
