title: Filter Operations
description: Filter queries with comparison operators and relation paths
---

`Filter(field, operator, value)` adds a condition to a query. Several `Filter()` calls are combined with `AND`.

```go
result, err := eng.Query("User").
    Filter("email", "eq", "ana@mail.com").
    Execute(ctx)
```

```sql
SELECT "id", "email", "name", ...
FROM "users"
WHERE "email" = $1
```

The value travels as a bound parameter (`$1 = String("ana@mail.com")`), not inside the SQL text.

## Operators

| Operator | SQL | Example |
|----------|-----|---------|
| `eq` | `=` | `Filter("age", "eq", 25)` |
| `neq` | `!=` | `Filter("status", "neq", "deleted")` |
| `gt` | `>` | `Filter("age", "gt", 18)` |
| `gte` | `>=` | `Filter("age", "gte", 18)` |
| `lt` | `<` | `Filter("total", "lt", 100)` |
| `lte` | `<=` | `Filter("total", "lte", 100)` |
| `like` | `LIKE` (contains) | `Filter("name", "like", "ana")` |

<Warning>
  **`in` is not supported.** It is rejected with an unsupported-operator error. To match several values, run the query once per value, or filter in your application.
</Warning>

Values can be `string`, `int`, `int64`, `float64` or `bool`. Any other Go type is converted to its string form with `fmt`, so pass dates as strings and convert other types yourself.

<Note>
  Float values are bound as `numeric`, so `Filter("total", "gt", 99.99)` compares exactly even against integer columns.
</Note>

## Multiple filters

```go
result, err := eng.Query("User").
    Filter("age", "gte", 18).
    Filter("age", "lte", 65).
    Execute(ctx)
```

```sql
WHERE "age" >= $1 AND "age" <= $2
```

There is no `OR` in the Go builder.

## Like (contains)

`like` means **contains**. ChameleonDB adds the wildcards and escapes any `%`, `_` or `\` in your value, so they match literally:

```go
eng.Query("User").Filter("name", "like", "ana").Execute(ctx)
```

```sql
WHERE "name" LIKE $1 ESCAPE '\'
-- $1 = String("%ana%")
```

`like` only accepts string values.

<Note>
  This differs from `like` in mutations (update and delete), where the pattern you pass is used as is. See [Safety Guards](/mutations/safety#filter-operators).
</Note>

## Null values

`Filter("age", "eq", nil)` generates `"age" = NULL`, which never matches in SQL. There is no `IS NULL` filter today. To find rows with a missing value, filter in your application or use a non-nullable field with a default.

## Filter on a related entity

A path of the form `relation.field` filters the main entity by a condition on a related one. The relation must be a **has-many** relation (declared with `via`):

```go
result, err := eng.Query("User").
    Select("id", "name").
    Filter("orders.total", "gt", 100).
    Execute(ctx)
```

```sql
SELECT DISTINCT "users"."id", "users"."name"
FROM "users"
INNER JOIN "orders" ON "orders"."user_id" = "users"."id"
WHERE "orders"."total" > $1
```

`DISTINCT` avoids duplicates when a user has several matching orders.

Constraints:

- Only one level: `orders.total` works, `orders.items.price` is rejected
- Filtering through a belongs-to relation (for example `Order` filtered by `user.name`) fails with a missing-foreign-key error
- With `DISTINCT`, PostgreSQL needs every `OrderBy` field to appear in the select list; if you use `Select()` with a relation filter, include the fields you sort by

## Relation filter plus include

The filter picks **which users** match. `Include("orders")` then loads **all** orders for those users, not only the ones that matched:

```go
result, err := eng.Query("User").
    Filter("orders.total", "gt", 100).
    Include("orders").
    Execute(ctx)
```

```sql
-- main query: users that have at least one order over 100 (JOIN as above)

-- eager query: every order of those users
SELECT "id", "total", ...
FROM "orders"
WHERE "user_id" = ANY($1)
```

## What is validated

The entity, the field or `relation.field` path and the operator are checked before SQL is generated. Value types are not checked; a wrong type is rejected by PostgreSQL.
