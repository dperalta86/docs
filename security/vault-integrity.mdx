description: 'SHA-256 hash checks for schema versions: what they detect and what they do not'
---

The Schema Vault stores a SHA-256 hash for every registered schema version and checks it before `migrate` runs. This detects unexpected changes to the recorded history.

<Note>
  This is **tamper detection, not tamper prevention or authentication**. The hash files sit next to the files they cover, so anyone who can rewrite both can make them agree. See [Limits](#limits).
</Note>

## Vault structure

```
.chameleon/vault/
├── manifest.json           # Current version and history
├── mode.json               # Integrity mode
├── mode_auth.json          # Password verifier
├── integrity.log           # Log of vault operations
├── versions/               # Snapshots of the merged schema
│   ├── v001.json
│   └── v002.json
└── hashes/                 # SHA-256 of each snapshot
    ├── v001.hash
    └── v002.hash
```

<Note>
  The vault is created by the first `chameleon migrate` (even `--dry-run`), not by `chameleon init`.
</Note>

## How it works

### 1. Registration

`chameleon migrate --apply` registers a version **before** it runs the SQL:

1. The merged schema text is saved to `versions/v002.json`
2. Its SHA-256 hash is saved to `hashes/v002.hash`
3. `manifest.json` is updated with the version, hash, timestamp, author, parent, a change summary and the source files
4. A `REGISTER` event is appended to `integrity.log`

`author` is the `USER` environment variable (`unknown` if unset).

### 2. Verification

Before it does anything else, `migrate` (and `verify`, on demand) checks every registered version:

```
for each version in the manifest:
    stored  = read hashes/<version>.hash
    content = read versions/<version>.json
    actual  = SHA-256(content)
    fail unless actual == stored and actual == manifest hash
```

### 3. Detection

If a snapshot, its hash file or the manifest entry was changed so that they disagree, `migrate` stops:

```
✗ INTEGRITY VIOLATION DETECTED
  ...
Recovery options:
   1. Run 'chameleon verify' for details
   2. Check .chameleon/vault/integrity.log
   3. Contact your DBA

✗ Migration aborted for safety
```

<Warning>
  Only `migrate` aborts. Other commands, such as `status` and `journal`, do not refuse to run on a vault that fails verification; run `chameleon verify` to check it.
</Warning>

## manifest.json

```json
{
  "current_version": "v002",
  "versions": [
    {
      "version": "v001",
      "hash": "3f2a8b9c...",
      "timestamp": "2026-11-03T10:30:00Z",
      "author": "dperalta",
      "parent": null,
      "locked": true,
      "changes_summary": "Initial schema",
      "files": ["schemas/example.cham"]
    },
    {
      "version": "v002",
      "hash": "7d4e1c2a...",
      "timestamp": "2026-11-03T15:45:00Z",
      "author": "dperalta",
      "parent": "v001",
      "locked": true,
      "changes_summary": "...",
      "files": ["schemas/example.cham"]
    }
  ],
  "paranoid_mode": "readonly"
}
```

`locked` is a flag in the manifest; it does not set any filesystem protection. `paranoid_mode` is a legacy copy of the mode in `mode.json`.

## Snapshots

Each `versions/vNNN.json` contains the **merged schema text** (the `.cham` source of all your schema files, merged) exactly as it was when the version was registered. The file name ends in `.json` for historical reasons.

Do not edit snapshots. Any change is reported as a hash mismatch.

## integrity.log

One line per event: a UTC timestamp, the event type in brackets, then key-value details.

```
2026-11-03T10:30:00Z [INIT]
2026-11-03T10:30:01Z [REGISTER] version=v001 ...
2026-11-03T10:30:02Z [MIGRATE] version=v001 status=applied duration=42ms
2026-11-03T15:45:00Z [MODE] action=mode_updated mode=standard
```

Event types written today:

| Event | When |
|-------|------|
| `INIT` | Vault created |
| `REGISTER` | New version registered |
| `MIGRATE` | Migration applied or failed |
| `MODE` | Mode changed, or a change denied |
| `MODE_AUTH` | Mode password set |
| `SCHEMA_PATH` | Schema paths changed |

Not logged today: `verify` runs and integrity violations. A failed `verify` or `migrate` check shows on the terminal and in the exit code but does not add a line to `integrity.log`, so monitor with `chameleon verify` rather than by searching the log.

<Warning>
  ChameleonDB only appends to `integrity.log`. The file is writable by anyone with access to the directory and is not protected against edits. Keep it in version control or ship it to a log system if you need a reliable record.
</Warning>

## Verifying

```bash
chameleon verify
```

```
Running Integrity Verification...

Vault:
  manifest.json is valid
  v001 integrity OK
  v002 integrity OK
  No tampering detected

Schema Files:
  schema *.cham exists
  Matches v002 hash

All checks passed
```

The exit code is `0` on success and `1` otherwise, so it fits in CI and hooks. A failing version is listed with its issue:

```
  v001 integrity FAILED
     hash mismatch (expected: ..., got: ...)
```

## Version history

```bash
chameleon journal schema          # all versions
chameleon journal schema v002     # one version: hash, author, parent, summary, files
```

## Recovery

If `verify` fails:

1. **Look at what changed.** `git status` and `git diff .chameleon/vault/` if the vault is committed. Review `integrity.log`.
2. **Restore the vault** from version control or a backup:

   ```bash
   git checkout -- .chameleon/vault/
   chameleon verify
   ```

3. **Investigate** who had write access to the directory (file ownership, OS audit logs, your Git history).
4. **Set a new mode password** if you suspect the password verifier was exposed:

   ```bash
   chameleon config auth set-password
   ```

If you have no backup, you can rebuild trust only by deciding which snapshot content is correct; ChameleonDB cannot do that for you.

## Limits

- **No authentication.** A matching hash proves the files agree with each other, not who wrote them.
- **Not covered by the hash check:** `mode.json`, `mode_auth.json` and `integrity.log`.
- **The merged schema the engine loads is not compared** with the vault's current hash when the engine starts. `chameleon verify` reports it; the engine does not enforce it.
- **Permissions.** Vault directories are created `0755` and files `0644`. Tighten them yourself (see [Best Practices](/security/best-practices)).
- **No automatic rollback or repair.**

## Best practices

- Never edit vault files by hand.
- Commit the vault (except `mode_auth.json`) so history is reviewed like code.
- Run `chameleon verify` in CI and before deployments.
- Back up `.chameleon/vault/`.
- Review vault changes in code review.
