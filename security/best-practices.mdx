<Warning>
  ChameleonDB is alpha software and has not been independently audited. These practices reduce risk; they do not make the current alpha suitable for untrusted input or for production data. See the [Security Overview](/security/overview).
</Warning>

## File permissions

ChameleonDB creates `.chameleon/` directories with mode `0755` and most files with `0644`; only `mode_auth.json` is created `0600`. Tighten the rest yourself after `migrate` has created the vault:

```bash
chmod -R go-rwx .chameleon/
```

Or, more explicitly:

```bash
chmod 700 .chameleon .chameleon/vault
chmod 600 .chameleon/vault/mode_auth.json
```

Check the result:

```bash
ls -la .chameleon/ .chameleon/vault/
```

## Mode password

```bash
chameleon config auth set-password
```

- ChameleonDB requires at least **8** characters. Use 16 or more, unique, from a password manager.
- It is stored as a salted single-round SHA-256 hash in `.chameleon/vault/mode_auth.json`. If that file leaks, a weak password can be brute-forced quickly.
- Rotate with the same command after personnel changes or suspected exposure.

### CI

There is no `--password` flag. Pass the password through the environment, from your secret store:

```yaml
env:
  CHAMELEON_MODE_PASSWORD: ${{ secrets.CHAMELEON_MODE_PASSWORD }}
  DATABASE_URL: ${{ secrets.DATABASE_URL }}

steps:
  - run: chameleon verify
  - run: chameleon config set mode=standard
  - run: chameleon migrate --apply
  - run: chameleon config set mode=readonly
```

Standard input piping (`<<<`) does not work: the prompt needs a terminal.

## Integrity modes

- Keep `readonly` as the resting mode in staging and production.
- Upgrade only for the migration and lock again immediately.
- Remember that the mode is a local safeguard: control who can run `migrate` with CI permissions, and who can change the database with PostgreSQL roles.

See [Mode Enforcement](/security/mode-enforcement).

## Secrets

ChameleonDB does not read `.env` files. Set `DATABASE_URL` and `CHAMELEON_MODE_PASSWORD` in your shell, a tool such as `direnv`, or your CI.

`.chameleon.yml` should reference the environment, not contain credentials:

```yaml
database:
  driver: postgresql
  connection_string: ${DATABASE_URL}
```

Add this to your `.gitignore`:

```gitignore
.env
.env.*
.chameleon/vault/mode_auth.json
.chameleon/state/
.chameleon/journal/
.chameleon/backups/
```

<Note>
  `.chameleon/state/schema.merged.cham` is generated by `migrate`, and `engine.NewEngine()` reads it at runtime. If you ignore `state/`, make sure your deployment runs `migrate --dry-run` (or otherwise produces that file) before the application starts.
</Note>

## What to commit

| Commit | Do not commit |
|--------|---------------|
| `.chameleon.yml` (no secrets) | `.chameleon/vault/mode_auth.json` |
| `schemas/*.cham` | `.env` files |
| `.chameleon/vault/manifest.json`, `versions/`, `hashes/`, `integrity.log` (optional, gives a shared history) | `.chameleon/state/`, `journal/`, `backups/` |
| | Anything containing passwords or connection strings |

### Pre-commit hook

```bash
#!/bin/bash
# .git/hooks/pre-commit

if git diff --cached --name-only | grep -qE '(^|/)\.env($|\.)|mode_auth\.json$'; then
  echo "Refusing to commit secrets"
  exit 1
fi

if [ -d .chameleon/vault ]; then
  chameleon verify > /dev/null || {
    echo "Vault integrity check failed"
    exit 1
  }
fi
```

## Database access

- Use a PostgreSQL role with the **least privilege** the application needs. Applications that only query do not need `CREATE`.
- Use a separate role for migrations.
- Set `sslmode` explicitly in the connection strings you give to the CLI:

  ```
  postgresql://user:pass@host:5432/db?sslmode=require
  ```

<Warning>
  Application code that connects with `eng.Connect(ctx, engine.ConnectorConfig{...})` always uses `sslmode=disable`; the config has no TLS option today. Run those connections over a trusted network or through a TLS-terminating proxy until this is fixed.
</Warning>

## Debug output

Debug output prints parameter values, except those of columns that look like secrets (`password`, `token`, `secret`, `hash`, ...), which are `[REDACTED]`. Emails, names and ids are printed, so do not enable debug output (`.Debug()` or `CHAMELEON_DEBUG`) where logs may contain personal data.

## Monitoring

`integrity.log` records `INIT`, `REGISTER`, `MIGRATE`, `MODE`, `MODE_AUTH` and `SCHEMA_PATH` events. It does not record verification failures, so do not rely on searching it for "violation". Instead:

```bash
# Periodic check (cron, CI schedule); exit code 0 = ok, 1 = problem
chameleon verify > /dev/null || echo "ChameleonDB vault check failed" | mail -s "ChameleonDB alert" you@example.com
```

Events worth alerting on:

```bash
grep -E "\[MODE\].*(mode_change_denied|mode=emergency|mode=privileged)" .chameleon/vault/integrity.log
grep -E "\[(MODE_AUTH|SCHEMA_PATH)\]" .chameleon/vault/integrity.log
```

The log is a plain file; ship it to a log system or keep it in version control if you need a reliable record.

## Backups

Back up what you cannot regenerate:

- `.chameleon/vault/` (excluding secrets handling as appropriate for your storage)
- `schemas/` and `.chameleon.yml`
- The database itself, with `pg_dump`. `migrate` does **not** create a backup, even with `features.backup_on_migrate` enabled.

```bash
tar -czf "vault-$(date +%Y%m%d).tar.gz" .chameleon/vault/
```

Test restores:

```bash
mkdir /tmp/vault-test
tar -xzf vault-20261103.tar.gz -C /tmp/vault-test
cd /tmp/vault-test && chameleon verify
```

## Audit review

```bash
chameleon journal last 100        # recent operations
chameleon journal errors          # failed operations
chameleon journal schema          # version history
grep MODE .chameleon/vault/integrity.log
```

There is no `journal export` command today; redirect the output if you need to keep it.

## Incident response

### Vault integrity failure

```bash
# 1. Stop running migrations
# 2. See what failed
chameleon verify

# 3. Compare with version control
git status .chameleon/vault/
git diff .chameleon/vault/

# 4. Restore a known-good vault
git checkout -- .chameleon/vault/
chameleon verify

# 5. Find out who had write access; rotate the mode password
chameleon config auth set-password
```

### Unexpected mode change

```bash
chameleon config get mode
chameleon config set mode=readonly
chameleon journal last 50
grep MODE .chameleon/vault/integrity.log
chameleon config auth set-password
```

Because `mode.json` is a plain file, an unexpected mode can also come from someone editing it directly; treat it as a possible access problem on the project directory.

### Suspected password exposure

```bash
chameleon config auth set-password   # rotate
chameleon verify
chameleon journal schema             # review recent versions
```

Update `CHAMELEON_MODE_PASSWORD` in every environment and in CI.

## Reporting a vulnerability

Use GitHub's private vulnerability reporting (**Security, Report a vulnerability**). Do not open a public issue.
