<Warning>
  ChameleonDB is **alpha software** and has not been independently audited. Do not use the current alpha with untrusted input or for production data. The project's [SECURITY.md](https://github.com/chameleon-db/chameleondb/blob/main/SECURITY.md) is the authoritative statement; if a page here goes beyond it, that is a documentation bug.
</Warning>

This page describes the security-relevant parts of ChameleonDB, the threats each one addresses, and where it stops.

## Summary

| Area | What it does | What it does not do |
|------|--------------|---------------------|
| Query and mutation generation | Binds values as parameters; validates and quotes identifiers | Does not check value types in the query builder |
| Schema Vault | Records versions with SHA-256 hashes and detects unexpected changes | Does not prevent changes or authenticate who made them |
| Integrity modes | Gates `migrate` and `introspect` behind a mode and a password | Is not access control; its files are editable |
| Audit logs | Records vault, migration and mode events | Are plain files; not tamper-proof |
| File permissions | You set them (see [Best Practices](/security/best-practices)) | ChameleonDB creates directories `0755` and files `0644`; only the password verifier is `0600` |

## Layers

### 1. Safe SQL generation

The most concrete protection in the current release.

- Filter, insert and update **values** are sent as bound parameters (`$1`, `$2`, ...), never written into the SQL text
- Table, column and relation names are **validated against the schema and quoted**
- `like` in the query builder is "contains", with wildcards in the value escaped
- Eager loading binds parent ids as one array (`= ANY($1)`)
- Operators that cannot be generated safely (`in`) and filter paths deeper than `relation.field` are rejected

A query-generation injection issue was fixed in v1.1.0-alpha. Details are in the project's [published security advisories](https://github.com/chameleon-db/chameleondb/security/advisories). If you run an earlier version, upgrade.

<Note>
  DDL generated by `migrate` is built from your schema files. Treat schema files as trusted code, review them like any other source, and do not generate them from untrusted input. Identifier validation for DDL is still being hardened.
</Note>

### 2. Hash integrity (Schema Vault)

Each registered schema version has a SHA-256 hash stored beside its snapshot. `migrate` and `verify` recompute and compare them. A mismatch aborts `migrate` and makes `verify` exit non-zero.

This detects accidental changes and edits made outside the tool. It does **not** stop a user who can rewrite both a snapshot and its hash, and it does not say who made a change. See [Vault Integrity](/security/vault-integrity).

### 3. Integrity modes

A local gate: in `readonly` (the default after the first migration), `migrate` and `introspect` stop. Leaving `readonly` needs a password. See [Mode Enforcement](/security/mode-enforcement).

The mode file and the password verifier are in `.chameleon/vault/`. Anyone who can write there can change them, so this protects against mistakes, not against someone with access to the project directory.

### 4. Vault check at engine start

`engine.NewEngine()` requires an initialized vault, verifies its hashes and loads the merged schema from `.chameleon/state/schema.merged.cham` (or `schema.merged_output`).

Be precise about the limits:

- The merged schema file the engine reads is **not compared** with the vault's current hash at startup. `chameleon verify` reports whether they match; the engine does not enforce it.
- `engine.NewEngineForCLI()` is exported and skips these checks. It exists for the CLI and tests; application code is not technically prevented from using it.

### 5. Audit trail

`.chameleon/vault/integrity.log` records `INIT`, `REGISTER`, `MIGRATE`, `MODE`, `MODE_AUTH` and `SCHEMA_PATH` events with a UTC timestamp, and the journal in `.chameleon/journal/` records operations. Both are plain files that ChameleonDB only appends to. Nothing prevents someone with file access from editing them, so treat them as an operational record.

## Threat model

### Addressed (within the limits above)

- **SQL injection through queries and mutations** - parameterization and identifier validation
- **Accidental schema changes through the CLI** - integrity mode in `readonly`
- **Accidental or casual edits to vault history** - hash checks on `migrate` and `verify`
- **Unfiltered updates and deletes** - blocked before SQL is generated

### Not addressed

<Warning>
  **Someone who can modify the project directory.** They can edit the vault, its hashes, the mode, the verifier and the logs together. Use version control, code review and OS permissions.
</Warning>

<Warning>
  **Compromise of the database or its credentials.** ChameleonDB does not secure PostgreSQL itself. Use database roles with least privilege, TLS and network controls.
</Warning>

<Warning>
  **Transport security from application code.** The `engine.ConnectorConfig` used by `eng.Connect()` builds a connection string with `sslmode=disable` and offers no option to change it. Connections made with the CLI (`migrate`) use the connection string you provide, so set `sslmode` there. Until TLS is configurable in `ConnectorConfig`, run application connections over a trusted network or a TLS-terminating proxy.
</Warning>

<Warning>
  **Secrets in debug output.** `.Debug()` on mutations prints the actual values, and query debug prints parameters. Do not enable it where logs hold sensitive data.
</Warning>

<Warning>
  **Weak passwords.** The mode password is stored as a salted single-round SHA-256 hash. Use a long, unique password and keep `mode_auth.json` out of version control.
</Warning>

## Checklist

```
Configuration:
[ ] Running v1.1.0-alpha or later
[ ] Directory permissions tightened (chmod 700 .chameleon)
[ ] Mode password set; mode_auth.json not committed
[ ] Mode left in readonly between migrations
[ ] DATABASE_URL in the environment, not in files

Verification:
[ ] chameleon verify passes (run it in CI)
[ ] Vault changes reviewed in code review
[ ] No secrets in .chameleon.yml

Database:
[ ] Least-privilege PostgreSQL role for the application
[ ] sslmode set explicitly in CLI connection strings
[ ] Backups taken before migrations
```

## Reporting a vulnerability

Do not open a public issue. Use GitHub's private vulnerability reporting: **Security, Report a vulnerability** on the repository.
