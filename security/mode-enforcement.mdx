title: 'Mode Enforcement'
description: 'A local gate on schema-changing commands, with password-protected upgrades'
---

Integrity Modes are a **local safeguard** on `chameleon migrate` and `chameleon introspect`. The mode is stored in the Schema Vault, and moving to a less restrictive mode asks for a password.

<Warning>
  This is not an access-control system. The mode and the password verifier are plain files in `.chameleon/vault/`; anyone who can write to that directory can change them without a password. The mode protects against accidents and casual changes through the CLI. For real authority, use CI permissions and PostgreSQL roles as well.
</Warning>

## The four modes

| Mode | Ring (naming only) | `migrate` and `introspect` | Also allows |
|------|--------------------|----------------------------|-------------|
| `readonly` (default) | R3 | Blocked once a schema version exists | - |
| `standard` | R2 | Allowed | - |
| `privileged` | R1 | Allowed | `config set schema-paths` |
| `emergency` | R0 | Allowed | `config set schema-paths` (typed confirmation) |

`readonly` is the only mode that changes what `migrate` and `introspect` do. The other three differ only in which `config` operations they allow. There is no direct SQL execution, no `--force` flag and no skipped integrity check in any mode: `privileged` and `emergency` run the same vault verification as `standard`.

<Info>
  The ring numbers come from Unix protection rings, where a lower number means more privilege. They are labels, not an isolation mechanism.
</Info>

## What `readonly` does

```bash
chameleon migrate --apply
```

```
✗ Read Only Paranoid Mode is active - schema modifications are blocked

ℹ To override (not recommended):
   1. Set mode password: chameleon config auth set-password
   2. Upgrade paranoid mode: chameleon config set mode=standard
   3. Fix integrity issues first

Error: readonly mode: schema locked
```

It applies to `migrate --apply`, `--dry-run` and `--check`, and to `introspect`. It does **not** affect queries or data mutations through the Go API: those do not read the mode.

`validate`, `status`, `verify`, `journal` and `config get` always run.

### First migration

`init` does not create the vault. The first `migrate` creates it, in `readonly`, and that migration is **not** blocked, because no version existed when it started. From then on `migrate` stops until you upgrade.

## Upgrading and downgrading

Moving to a **less** restrictive mode asks for the mode password. Moving to a **more** restrictive one does not.

```bash
chameleon config auth set-password        # first time; min 8 characters
chameleon config set mode=standard        # asks for the password
chameleon migrate --apply
chameleon config set mode=readonly        # downgrade: no password
```

```
Enter mode password (or set CHAMELEON_MODE_PASSWORD env var): ********
✓ Paranoid Mode updated: standard
```

Without a configured password, an upgrade fails with `mode password not configured`.

For CI, set `CHAMELEON_MODE_PASSWORD`; the prompt needs a terminal, so piping the password to standard input does not work.

## Password storage

- Stored as a **salted SHA-256 hash** in `.chameleon/vault/mode_auth.json`, file mode `0600`
- One round of SHA-256 is fast to brute-force if the file leaks, so use a long, unique password
- The default `.chameleon/.gitignore` does not ignore `vault/`; add `.chameleon/vault/mode_auth.json` to your own `.gitignore`

## What is checked, and where

```
chameleon migrate --apply
        ↓
1. Create the vault if missing (mode readonly)
        ↓
2. Verify every version's hash       ← abort on mismatch
        ↓
3. If a version exists and mode is readonly   ← stop
        ↓
4. Merge and validate schema files
        ↓
5. Register a version, run the SQL
```

The mode is read from `.chameleon/vault/mode.json`, which the hash check does not cover.

## Checking the mode

```bash
chameleon config get mode
```

```
readonly
```

`chameleon status` also shows it.

## Audit

Mode changes and denied attempts go to the journal and to `integrity.log` as `MODE` events; setting a password writes `MODE_AUTH`, and changing schema paths writes `SCHEMA_PATH`:

```
2026-11-03T15:45:00Z [MODE] action=mode_updated mode=standard
2026-11-03T15:46:10Z [MODE] action=mode_change_denied mode=privileged reason=invalid_mode_password
```

The log does not record which OS user made the change. The journal (`chameleon journal last`) records the operation; the vault's version entries record `author` from the `USER` variable for migrations only.

<Warning>
  Both files are plain, writable files. Treat them as an operational record, not as tamper-proof evidence.
</Warning>

## Strategy by environment

| Environment | Suggested mode | Notes |
|-------------|---------------|-------|
| Development | `standard` | Developers iterate on schemas |
| CI | `standard`, then back to `readonly` | Password from the secret store |
| Staging and production | `readonly` | Upgrade for the migration only |

Keep production in `readonly` and unlock for the migration:

```bash
chameleon verify
chameleon config set mode=standard
chameleon migrate --dry-run
chameleon migrate --apply
chameleon config set mode=readonly
chameleon config get mode
```

## Best practices

1. Set a password as soon as the vault exists.
2. Keep `readonly` as the resting state; upgrade for the change and lock again.
3. Keep `mode_auth.json` out of version control.
4. Pass the password in CI through your secret store and `CHAMELEON_MODE_PASSWORD`.
5. Review `integrity.log` and the journal for mode changes.
6. Rotate the password after personnel changes (`chameleon config auth set-password`).
