title: "Constraints"
description: "Primary keys, unique, nullable and default values in ChameleonDB schemas"
---

Constraints are modifiers written after a field's type. They become column constraints in the generated `CREATE TABLE`, and PostgreSQL enforces them.

```text
fieldName: type primary unique nullable default value @annotation,
```

Modifiers can appear in any order after the type. An [annotation](/schema/annotations), if present, goes last.

## Primary keys

```chameleon
entity User {
    id: uuid primary,
    email: string,
}
```

**Rules checked by `validate`:**

- Each entity has exactly one `primary` field

```
Entity 'User' has no primary key
Entity 'User' has multiple primary keys: ["id", "email"]
```

**SQL:** `id UUID PRIMARY KEY`

<Warning>
  Name your primary key `id`. A has-many relation generates `FOREIGN KEY (...) REFERENCES parent_table(id)`, with the column name fixed to `id`, and eager loading also expects `id`. An entity with a different primary key name (for example `code: string primary`) works on its own, but if it is the parent of a has-many relation the migration fails in PostgreSQL because the referenced `id` column does not exist.
</Warning>

Other limits:

- Composite primary keys are not supported.
- `primary nullable` is accepted by the checker, but the generated column is simply `PRIMARY KEY`, which is always `NOT NULL`. Do not combine them.
- A primary key can have a `default` (for example `default uuid()`), but not an annotation.

## Unique

```chameleon
entity User {
    id: uuid primary,
    email: string unique,
    username: string unique,
}
```

**SQL:** `email VARCHAR NOT NULL UNIQUE`

- Composite unique constraints are not supported.
- PostgreSQL treats `NULL` values as distinct, so a `unique nullable` column allows several `NULL`s.
- A `unique` field cannot have an annotation.

## Nullable

Fields are `NOT NULL` unless marked `nullable`:

```chameleon
entity User {
    id: uuid primary,
    email: string,
    bio: string nullable,
    deleted_at: timestamp nullable,
}
```

**SQL:**

```sql
email VARCHAR NOT NULL,
bio VARCHAR,
deleted_at TIMESTAMP
```

Relations take no modifiers, so `author: User nullable,` is a parse error. For an optional relation, make the **foreign key field** nullable:

```chameleon
entity Post {
    id: uuid primary,
    author_id: uuid nullable,
    author: User,
}

entity User {
    id: uuid primary,
    posts: [Post] via author_id,
}
```

<Warning>
  Use `nullable` sparingly; required fields make the model clearer.
</Warning>

## Default values

```chameleon
entity Account {
    id: uuid primary default uuid(),
    role: string default "user",
    active: bool default true,
    score: int default 0,
    created_at: timestamp default now(),
}
```

| Type | Default |
|------|---------|
| `uuid` | `uuid()` or `uuid_v4()` |
| `string` | `"text"` |
| `int` | integer literal |
| `decimal`, `float` | integer or decimal literal |
| `bool` | `true` or `false` |
| `timestamp` | `now()` |

`vector(N)` and array fields cannot have defaults. See [Field Types](/schema/fields-types#default-values) for the SQL each one produces and the error messages.

## Combining modifiers

```chameleon
entity User {
    id: uuid primary default uuid(),
    email: string unique,
    nickname: string unique nullable,
    created_at: timestamp default now(),
    name: string nullable default "anonymous",
}
```

`nullable unique` and `unique nullable` are equivalent. The type always comes first, directly after the colon.

## What `validate` checks

| Rule | Checked |
|------|---------|
| Exactly one primary key | Yes |
| Default matches the type | Yes |
| No annotation on `primary` or `unique` fields | Yes |
| `primary` combined with `nullable` | No |
| Primary key named `id` | No |
| Composite keys, `CHECK`, indexes | Not supported |

## Enforcement at runtime

The constraints live in the database, so they are enforced once the table exists. ChameleonDB translates the PostgreSQL error into a typed error:

```go
_, err := db.Insert("User").
    Set("id", uuid.New().String()).
    Set("email", "ana@mail.com").
    Execute(ctx)
// If the email exists:
// UniqueConstraintError: Field 'email' must be unique
```

A missing required column produces `NotNullError: Field 'email' cannot be null`. See [Insert](/mutations/insert) for the full list of errors.

<Note>
  Migrations only create tables that do not exist yet. Adding `unique` or removing `nullable` on a field of an existing table does **not** change that table. Apply the change in PostgreSQL yourself. See [Migrations](/guides/migrations).
</Note>

## Common patterns

### Soft deletes

```chameleon
entity User {
    id: uuid primary,
    email: string unique,
    deleted_at: timestamp nullable,
}
```

### Audit timestamps

```chameleon
entity Post {
    id: uuid primary,
    title: string,
    created_at: timestamp default now(),
    updated_at: timestamp nullable,
}
```

### Business identifier next to the key

```chameleon
entity Product {
    id: uuid primary,
    sku: string unique,
    name: string,
}
```
