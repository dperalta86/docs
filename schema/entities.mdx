Entities are the building blocks of a ChameleonDB schema. Each entity becomes one PostgreSQL table and holds fields and relations.

## Entity definition

An entity is the `entity` keyword, a name and a block of members. **Every member ends with a comma**, including the last one:

```chameleon
entity User {
    id: uuid primary,
    email: string unique,
    name: string,
    created_at: timestamp default now(),
}
```

A member without its trailing comma is a parse error:

```text
entity U {
    id: uuid primary
}
```

```text
Parse error at line 3, column 1: Unexpected token: Token(37, "}"), expected one of: ",", "@cache", "@ml", "@olap", "@vector", "default", "nullable", "primary", "unique"
```

Line comments start with `//`.

## Naming

The parser accepts any identifier that starts with a letter or `_` and continues with letters, digits or `_`. By convention:

- Entity names are PascalCase and singular: `User`, `OrderItem`
- Field and relation names are snake_case: `created_at`, `user_id`

Some words are reserved by the language and cannot be field names, for example `default`.

### Table names

The table name is derived from the entity name: PascalCase becomes snake_case and an `s` is appended. There is no irregular-plural handling.

| Entity | Table |
|--------|-------|
| `User` | `users` |
| `OrderItem` | `order_items` |
| `UserProfile` | `user_profiles` |
| `Category` | `categorys` |
| `users` | `userss` |

<Warning>
  Because the suffix is always `s`, `Category` becomes `categorys`. Name entities with this rule in mind, and keep them singular so you do not end up with `userss`. The same table name is used by migrations, queries and mutations.
</Warning>

## Members

An entity contains **fields** and **relations**.

### Fields

Data columns, with a type, optional modifiers and an optional [annotation](/schema/annotations):

```chameleon
entity Product {
    id: uuid primary,
    name: string,
    price: decimal,
    stock: int,
}
```

### Relations

Links to other entities. See [Relations](/schema/relations).

```chameleon
entity Order {
    id: uuid primary,
    user_id: uuid,
    user: User,                       // belongs-to
    items: [OrderItem] via order_id,  // has-many
}

entity User {
    id: uuid primary,
}

entity OrderItem {
    id: uuid primary,
    order_id: uuid,
}
```

A relation declares a link; the foreign key itself is an ordinary field (`user_id`) that you declare yourself.

## Complete example

```chameleon
entity User {
    id: uuid primary,
    email: string unique,
    name: string,
    age: int nullable,
    created_at: timestamp default now(),

    orders: [Order] via user_id,
    posts: [Post] via author_id,
}

entity Order {
    id: uuid primary,
    total: decimal,
    status: string,
    created_at: timestamp default now(),
    user_id: uuid,

    user: User,
    items: [OrderItem] via order_id,
}

entity OrderItem {
    id: uuid primary,
    quantity: int,
    price: decimal,
    order_id: uuid,

    order: Order,
}

entity Post {
    id: uuid primary,
    title: string,
    content: string,
    author_id: uuid,
    created_at: timestamp default now(),

    author: User,
}
```

## What `validate` checks

`chameleon validate` runs the type checker. For entities it reports:

| Rule | Error message |
|------|---------------|
| Exactly one primary key | `Entity 'X' has no primary key` / `Entity 'X' has multiple primary keys: [...]` |
| Unique entity names | `Duplicate entity name 'X' (first defined at #1, redefined at #2)` |
| Unique field names | `Duplicate field name 'f' in entity 'X'` |
| Relation targets exist | `Entity 'X' references unknown entity 'Y' in relation 'r'` |
| Has-many `via` field exists in the target | `Relation 'r' in 'X' references foreign key 'fk', but 'Y' has no such field` |
| No cycles of has-many relations | `Circular dependency detected: [...]` |
| Annotation and default rules | See [Annotations](/schema/annotations) and [Constraints](/schema/constraints) |

<Note>
  The checker does not look at foreign key **types**, and it does not require belongs-to relations to have a matching field. See [Relations](/schema/relations#what-is-not-checked).
</Note>

## Changing an entity later

Migrations only create missing tables (`CREATE TABLE IF NOT EXISTS`). Editing an entity that already has a table, whether adding a field, changing a type or adding a constraint, registers a new schema version but **does not alter the table**. Make those changes in PostgreSQL yourself. See [Migrations](/guides/migrations).

## Best practices

<Tip>
  **Keep entities focused.** One entity, one domain concept.
</Tip>

<Tip>
  **Name the primary key `id`.** Has-many foreign keys always reference `id` on the parent table, and eager loading expects it. See [Constraints](/schema/constraints#primary-keys).
</Tip>

<Tip>
  **Group members with comments** (fields, relations, annotations) for readability.
</Tip>
