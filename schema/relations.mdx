A relation links two entities. ChameleonDB has two kinds: **has-many** (with `via`) and **belongs-to**.

## Has-many

The parent declares a collection and names the foreign key field that lives in the **target** entity:

```chameleon
entity User {
    id: uuid primary,
    orders: [Order] via user_id,
}

entity Order {
    id: uuid primary,
    user_id: uuid,
}
```

Syntax: `name: [Target] via foreign_key_field,`

`via user_id` means "find the `Order` rows where `order.user_id = user.id`". This is the declaration that creates the database constraint:

```sql
CREATE TABLE IF NOT EXISTS orders (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

The foreign key has no `ON DELETE` rule, so deleting a parent that still has children fails with a `ForeignKeyError`.

## Belongs-to

The child declares a single reference:

```chameleon
entity Order {
    id: uuid primary,
    user_id: uuid,
    user: User,
}

entity User {
    id: uuid primary,
    orders: [Order] via user_id,
}
```

Syntax: `name: Target,`

<Warning>
  A belongs-to relation does not infer or create anything on its own. The `user_id` field must be declared by you, the checker does not verify that it exists, and **no foreign key constraint is generated from it**. Only a has-many on the other side produces the constraint. Declare both sides if you want the constraint.
</Warning>

## Querying relations

Eager loading (`Include`) and filtering on a related field (`Filter("orders.total", ...)`) work from the **has-many** side. See [Relations in queries](/queries/relations).

## Both sides

```chameleon
entity User {
    id: uuid primary,
    orders: [Order] via user_id,
    posts: [Post] via author_id,
}

entity Order {
    id: uuid primary,
    total: decimal,
    user_id: uuid,
    user: User,
}

entity Post {
    id: uuid primary,
    title: string,
    author_id: uuid,
    author: User,
}
```

## Optional relations

Relations accept no modifiers. Make the foreign key field nullable:

```chameleon
entity Order {
    id: uuid primary,
    coupon_id: uuid nullable,
    coupon: Coupon,
}

entity Coupon {
    id: uuid primary,
    orders: [Order] via coupon_id,
}
```

`coupon: Coupon nullable,` is a parse error.

## Many-to-many

There is no direct many-to-many. Use a join entity, with a has-many from each side so that both foreign keys are created:

```chameleon
entity Post {
    id: uuid primary,
    title: string,
    post_tags: [PostTag] via post_id,
}

entity Tag {
    id: uuid primary,
    name: string,
    post_tags: [PostTag] via tag_id,
}

entity PostTag {
    id: uuid primary,
    post_id: uuid,
    tag_id: uuid,
    post: Post,
    tag: Tag,
}
```

This produces `post_tags` with `FOREIGN KEY (post_id) REFERENCES posts(id)` and `FOREIGN KEY (tag_id) REFERENCES tags(id)`.

## What `validate` checks

| Rule | Error |
|------|-------|
| Target entity exists | `Entity 'X' references unknown entity 'Y' in relation 'r'` |
| `via` field exists in the target | `Relation 'r' in 'X' references foreign key 'fk', but 'Y' has no such field` |
| No cycle of has-many relations | `Circular dependency detected: ["U", "O", "U"]` |

### What is not checked

- **Foreign key type.** A `via` field of type `string` pointing at a `uuid` primary key passes `validate`, and the migration then fails in PostgreSQL. Keep the types identical.
- **The belongs-to field.** `author: User` without any `author_id` passes.
- **The parent's primary key name.** The generated constraint references `parent_table(id)`.

## Limitations

### No self-referential relations

A has-many that points at its own entity is reported as a cycle:

```chameleon
entity Category {
    id: uuid primary,
    parent_id: uuid nullable,
    children: [Category] via parent_id,
}
```

```
Circular dependency detected: ["Category", "Category"]
```

The same happens when two entities have a has-many to each other. Cycles made only of belongs-to relations are allowed.

For a tree, keep the foreign key as a plain field and resolve the hierarchy in your code:

```chameleon
entity Category {
    id: uuid primary,
    name: string,
    parent_id: uuid nullable,
}
```

Note that PostgreSQL gets no foreign key for `parent_id` in that case.

### Other limits

- No `ON DELETE` / `ON UPDATE` rules
- No composite keys
- Foreign keys always reference the `id` column

## Best practices

<Tip>
  **Name foreign keys `{entity}_id`.**
</Tip>

<Tip>
  **Declare both sides** so the database constraint exists and queries can start from either entity.
</Tip>

<Tip>
  **Give the foreign key the same type as the parent's `id`**, since `validate` will not.
</Tip>
