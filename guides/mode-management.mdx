title: Managing Integrity Modes
description: Lock and unlock schema-changing commands with the integrity mode and its password
---

The integrity mode is a **local safeguard** on `chameleon migrate` and `chameleon introspect`. This page is the practical guide; [Integrity Modes](/concepts/integrity-modes) explains the model and its limits.

<Warning>
  The mode and the password verifier are plain files in `.chameleon/vault/`. The mode protects against accidents and casual changes through the CLI. It is not an access-control system: anyone who can write to that directory can change it. Control who may change schemas with your CI permissions and PostgreSQL roles as well.
</Warning>

## Overview

| Mode | Default | `migrate` and `introspect` | Also allows |
|------|---------|----------------------------|-------------|
| `readonly` | yes | Blocked once a schema version exists | - |
| `standard` | no | Allowed | - |
| `privileged` | no | Allowed | `config set schema-paths` |
| `emergency` | no | Allowed | `config set schema-paths` (with a typed confirmation) |

`readonly` is the only mode that changes what `migrate` and `introspect` do. The other three currently differ only in which `config` operations they allow.

<Info>
  Moving to a **less restrictive** mode (for example `readonly` to `standard`) asks for the mode password. Moving to a **more restrictive** one does not.
</Info>

## When the mode exists

`chameleon init` does not create the vault. The first `chameleon migrate` does, in `readonly` mode, and that first migration is **not** blocked. From then on `migrate` and `introspect` stop until you upgrade. All `config` commands need the vault, so they fail with `vault not initialized. Run 'chameleon migrate' first` before it exists.

## Set a password

```bash
chameleon config auth set-password
```

```
Choose mode password (min 8 chars): ********
✓ Mode password configured
```

- Minimum 8 characters.
- Stored as a **salted SHA-256 hash** in `.chameleon/vault/mode_auth.json` (file mode `0600`). One round of SHA-256 is fast to brute-force if the file leaks, so use a long, unique password.
- The default `.chameleon/.gitignore` does not ignore `vault/`. Add `.chameleon/vault/mode_auth.json` to your own `.gitignore`.
- Without a password, an upgrade fails with `mode password not configured`.

For non-interactive use, set `CHAMELEON_MODE_PASSWORD`.

## Check the mode

```bash
chameleon config get mode
```

```
readonly
```

`chameleon status` also shows it.

## Upgrade

```bash
chameleon config set mode=standard
```

```
Enter mode password (or set CHAMELEON_MODE_PASSWORD env var): ********
✓ Paranoid Mode updated: standard
```

## Downgrade

```bash
chameleon config set mode=readonly
```

```
✓ Paranoid Mode updated: readonly
```

## What each command does

| Command | `readonly` | `standard` and above |
|---------|-----------|----------------------|
| `migrate --apply`, `--dry-run`, `--check` | Stops once a version exists | Runs |
| `introspect` | Stops once a version exists | Runs |
| `validate`, `status`, `verify`, `journal`, `config get` | Run | Run |

Note that `migrate --dry-run` is also blocked in `readonly` after the first version, not only `--apply`.

## Workflows

### Local development

```bash
chameleon config set mode=standard
chameleon migrate --apply
# ... edit the schema ...
chameleon migrate --apply
```

### CI

The prompt needs a terminal, so pass the password through the environment, from your secret store:

```bash
export CHAMELEON_MODE_PASSWORD="$MODE_PASSWORD"   # from CI secrets
chameleon config set mode=standard
chameleon migrate --apply
chameleon config set mode=readonly
```

<Warning>
  Piping the password on standard input (`<<<` or `echo ... |`) does not work: the prompt reads from the terminal, and without one the command fails with `interactive password input is unavailable; set CHAMELEON_MODE_PASSWORD env var`.
</Warning>

### An authorized change in a locked project

```bash
chameleon status                       # check the mode
chameleon config set mode=standard     # password
chameleon migrate --dry-run            # read the SQL
chameleon migrate --apply
chameleon config set mode=readonly     # lock again
```

### Changing schema paths

`schema-paths` changes where schemas are loaded from, so it needs `privileged` or `emergency`, existing non-symlink paths and a confirmation:

```bash
chameleon config set mode=privileged
chameleon config set schema-paths=schemas/,legacy/schemas/
```

## Audit

Mode changes, denied attempts and schema-path changes are written to the journal and to `.chameleon/vault/integrity.log`:

```bash
chameleon journal last 50
grep MODE .chameleon/vault/integrity.log
```

```
2026-11-03T10:30:00Z [MODE] action=mode_updated mode=standard
2026-11-03T10:31:12Z [MODE] action=mode_change_denied mode=standard reason=invalid_mode_password
```

Both are plain files. They are an operational record, not tamper-proof evidence.

## Troubleshooting

### `mode password not configured`

```bash
chameleon config auth set-password
```

### `invalid mode password`

Re-enter it or check `CHAMELEON_MODE_PASSWORD`. The attempt is logged.

### `readonly mode: schema locked`

Upgrade the mode as shown above.

### Forgot the password

The gate is local: if you own the project directory, remove `.chameleon/vault/mode_auth.json` and set a new password. That also shows why the mode is a safeguard and not a security boundary. Do it only with authorization.

## Best practices

1. Set a password as soon as the vault exists, and keep `mode_auth.json` out of version control.
2. Keep `readonly` as the resting state; upgrade for the change and lock again.
3. Pass the password through your CI secret store and `CHAMELEON_MODE_PASSWORD`.
4. Review `integrity.log` and the journal for mode changes.
5. Enforce who may change schemas in CI and PostgreSQL as well.
