title: Migration Workflow
description: How ChameleonDB generates and applies migrations, and records them in the Schema Vault
---

`chameleon migrate` loads your schema files, registers each change as a version in the [Schema Vault](/concepts/schema-vault), generates PostgreSQL DDL and optionally applies it.

<Warning>
  **Migrations are create-only today.** The generated script contains one `CREATE TABLE IF NOT EXISTS` per entity and nothing else: no `DROP`, no `ALTER`. It will not delete your data, and it will not change tables that already exist. A new column or a type change in your schema is **not** applied to an existing table; apply those changes yourself. Applying differences is planned work.
</Warning>

## What `migrate` does

- Merges all `.cham` files from `schema.paths` and validates the result
- Registers a new schema version in the vault when the schema changed
- Verifies vault integrity before it does anything else
- Respects the integrity mode (`readonly` stops it once a version exists)
- Generates the SQL and, with `--apply`, runs it
- Records the result in the journal and `integrity.log`, and lets you retry a failed attempt

It does **not** compare your schema with the live database.

## Commands

### Preview

```bash
chameleon migrate              # same as --check
chameleon migrate --dry-run    # print the SQL, do not apply
```

Both print the generated SQL and stop. They do not register a version and do not connect to the database. They do create the vault on first use and write the merged schema to `.chameleon/state/schema.merged.cham`.

```
─────────────────────────────────────────────────
Migration SQL:
─────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS users (
    id UUID PRIMARY KEY,
    email VARCHAR NOT NULL UNIQUE,
    name VARCHAR NOT NULL
);
─────────────────────────────────────────────────

ℹ Dry-run mode. Use --apply to execute migration.
```

Columns are ordered primary key first, then alphabetically, so the same schema always produces the same SQL.

### Apply

```bash
export DATABASE_URL="postgresql://user:password@localhost:5432/mydb"
chameleon migrate --apply
```

```
ℹ Registering new schema version...
✓ Registered as v001 (hash: 3f2a8b9c1d4e...)
ℹ Connecting to database...
✓ Connected to database
ℹ Applying migration...
✓ Migration applied successfully

✓ Migration completed successfully!

Summary:
  Version:  v001
  Hash:     3f2a8b9c1d4e5f60...
  Duration: 42ms
  Status:   applied
```

The first `--apply` creates the vault and registers `v001`.

## Workflow

<Steps>
  <Step title="Edit the schema">
    ```chameleon
    entity User {
        id: uuid primary default uuid(),
        email: string unique,
        name: string,
        age: int nullable,
    }
    ```
  </Step>

  <Step title="Validate">
    ```bash
    chameleon validate schemas/example.cham
    ```

    This checks one file. `migrate` validates the merged schema as well.
  </Step>

  <Step title="Preview and read the SQL">
    ```bash
    chameleon migrate --dry-run
    ```

    Remember that the script only creates missing tables. If `users` already exists, adding `age` to the schema produces the same `CREATE TABLE IF NOT EXISTS`, which does nothing to the existing table.
  </Step>

  <Step title="Unlock if needed">
    ```bash
    chameleon config get mode
    chameleon config set mode=standard     # asks for the mode password
    ```

    See [Managing Integrity Modes](/guides/mode-management).
  </Step>

  <Step title="Apply">
    ```bash
    chameleon migrate --apply
    ```

    A new version (`v002`, and so on) is registered **before** the SQL runs.
  </Step>

  <Step title="Check">
    ```bash
    chameleon verify
    chameleon journal schema
    ```
  </Step>
</Steps>

## Changing existing tables

Because `migrate` does not alter tables, apply changes to existing tables by hand:

```sql
ALTER TABLE users ADD COLUMN age INTEGER;
```

Then run `chameleon migrate --apply` so that the new schema is registered as a version.

<Warning>
  The vault records the version as `applied` when the script runs without error, even if it changed nothing because the tables already existed. The version history tracks your schema, not the state of the database. Keep your own record of manual DDL.
</Warning>

## Vault integration

Every change registers an entry in `.chameleon/vault/` with a hash, a parent and the files that were merged:

```
.chameleon/vault/
├── manifest.json
├── mode.json
├── mode_auth.json
├── integrity.log
├── versions/        # v001.json, v002.json ... (the merged schema text)
└── hashes/          # v001.hash, v002.hash ...
```

View the history:

```bash
chameleon journal schema
chameleon journal schema v002
chameleon journal migrations
```

## Retry after a failure

If the connection or the SQL fails, the version stays registered and the migration is recorded as `failed`. Run `chameleon migrate --apply` again without changing the schema:

```
⚠ Schema unchanged, but latest version v002 is not applied to database
```

It generates the SQL again and retries.

## Integrity verification

Every `migrate` first checks that each version's snapshot still matches its recorded hash. On a mismatch it stops:

```
✗ INTEGRITY VIOLATION DETECTED
  ...
Recovery options:
   1. Run 'chameleon verify' for details
   2. Check .chameleon/vault/integrity.log
   3. Contact your DBA

✗ Migration aborted for safety
```

This detects changes to the vault files; it does not prove who made them. See [Schema Vault](/concepts/schema-vault#what-the-vault-does-not-do).

## Environment

`DATABASE_URL` is read through `${DATABASE_URL}` in `.chameleon.yml`. Export it in your shell or CI environment. ChameleonDB does not load `.env` files by itself; use your shell, `direnv` or your CI to set it, and keep it out of version control.

## Limits to know

- **No backup.** `features.backup_on_migrate` is not implemented; `migrate --apply` prints a warning saying no backup was created. Back up with `pg_dump` yourself.
- **Not wrapped in a transaction.** The script runs as one statement batch; do not assume atomic rollback.
- **No rollback command.**
- **Timeouts.** 30 seconds for the command, 10 seconds to connect.
- **TLS is not enforced.** Set `sslmode` explicitly in remote connection strings.

## Common issues

### `readonly mode: schema locked`

```bash
chameleon config auth set-password     # first time only
chameleon config set mode=standard
```

### `failed to connect to database`

Check `DATABASE_URL`, that PostgreSQL is reachable and that the user can create tables.

### `integrity check failed`

Someone changed vault files, or a file is corrupted. Run `chameleon verify` and review `.chameleon/vault/integrity.log`. Restore the vault from version control or a backup.

### `vault not initialized` (from `config`)

The vault is created by the first `chameleon migrate`, not by `init`:

```bash
chameleon migrate --dry-run
```

## Best practices

- Read `--dry-run` before every `--apply`.
- Keep `readonly` as the resting mode and unlock for the change.
- Back up the database before manual DDL.
- Commit the vault (except `mode_auth.json`) if you want a shared history.
- Run `chameleon verify` in CI.
