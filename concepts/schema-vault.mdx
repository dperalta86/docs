---
title: Schema Vault
description: Versioned schema snapshots with hash checks, stored in your project
---

The **Schema Vault** records each version of your schema in `.chameleon/vault/`, with a SHA-256 hash per version and an append-only-by-convention log. ChameleonDB checks those hashes before it migrates, so accidental or casual changes to the recorded history are detected.

## Overview

Schema evolution is usually tracked loosely: migration files, a table in the database, a wiki. The vault gives you one local, versioned record of what the schema was at each migration, and a way to notice when that record no longer matches itself.

<Note>
  The vault detects inconsistencies. It does not prevent them and it does not authenticate who made a change. Hashes are stored next to the files they cover, so anyone who can rewrite both can make them agree. See [What the vault does not do](#what-the-vault-does-not-do).
</Note>

## What it gives you

- **Versioned snapshots** - Each migration that changes the schema registers `v001`, `v002`, and so on
- **Hash verification** - SHA-256 of each snapshot is checked before `migrate` runs
- **Lineage** - Each version records its parent
- **A log** - `integrity.log` records vault operations (INIT, REGISTER, MIGRATE, MODE, ...)
- **No setup** - The vault is created by the first `chameleon migrate`

## Structure

```
.chameleon/vault/
├── manifest.json       # Current version and history
├── mode.json           # Current integrity mode
├── mode_auth.json      # Password verifier (salt + hash)
├── integrity.log       # Log of vault operations
├── versions/
│   ├── v001.json       # Snapshot of the merged schema
│   └── v002.json
└── hashes/
    ├── v001.hash       # SHA-256 of the snapshot
    └── v002.hash
```

### manifest.json

```json
{
  "current_version": "v002",
  "versions": [
    {
      "version": "v001",
      "hash": "3f2a8b9c...",
      "timestamp": "2026-11-03T10:30:00Z",
      "author": "dperalta",
      "parent": null,
      "locked": true,
      "changes_summary": "Initial schema",
      "files": ["schemas/example.cham"]
    },
    {
      "version": "v002",
      "hash": "7d4e1c2a...",
      "timestamp": "2026-11-03T15:45:00Z",
      "author": "dperalta",
      "parent": "v001",
      "locked": true,
      "changes_summary": "...",
      "files": ["schemas/example.cham"]
    }
  ],
  "paranoid_mode": "readonly"
}
```

`author` comes from the `USER` environment variable (`unknown` if unset). `paranoid_mode` is a legacy copy; the mode itself lives in `mode.json`. `locked` is a flag in the manifest, not a filesystem protection.

### versions/

Each `vNNN.json` holds the merged schema text exactly as it was when the version was registered (the `.cham` source of all your schema files, merged). The extension is `.json` for historical reasons; the content is the schema source.

### hashes/

One file per version with the SHA-256 of the corresponding snapshot.

### integrity.log

One line per event, with a UTC timestamp, the action and key-value details:

```
2026-11-03T10:30:00Z [INIT]
2026-11-03T10:30:01Z [REGISTER] version=v001 ...
2026-11-03T10:30:02Z [MIGRATE] version=v001 status=applied duration=42ms
```

The log is appended to and never rewritten by ChameleonDB. Nothing stops someone with file access from editing it.

## How it works

```bash
chameleon migrate --dry-run      # preview; creates the vault if missing
chameleon migrate --apply        # register a version and apply
```

On each `migrate`:

1. The vault is created if it does not exist (mode `readonly`).
2. Every registered version is verified: the snapshot must hash to the value in `hashes/` **and** in the manifest. A mismatch aborts the command.
3. If a version already exists and the mode is `readonly`, the command stops. See [Integrity Modes](/concepts/integrity-modes).
4. The schema files from `schema.paths` are merged and validated, and compared with the current version by hash.
5. With `--apply`: a new version is registered **before** the SQL runs, then the SQL is executed. If execution fails, the version stays registered and the migration is recorded as failed; running `migrate --apply` again retries it.

If nothing changed, no new version is created.

<Warning>
  A version is recorded as `applied` when the script runs without error. `migrate` is currently create-only, so a changed schema can register a new version while existing tables stay as they were. The version history tracks your schema, not the live state of the database.
</Warning>

## Verifying

```bash
chameleon verify
```

```
Running Integrity Verification...

Vault:
  manifest.json is valid
  v001 integrity OK
  No tampering detected

Schema Files:
  schema *.cham exists
  Matches v001 hash

All checks passed
```

If a snapshot or hash has been modified, the failing version is listed and the command exits with a non-zero code. `chameleon migrate` runs the same check first and aborts:

```
✗ INTEGRITY VIOLATION DETECTED
  ...
✗ Migration aborted for safety
```

## Version history

```bash
chameleon journal schema          # all versions
chameleon journal schema v002     # one version: hash, author, parent, summary, files
```

## What the vault does not do

- **It does not authenticate authorship.** `author` is read from an environment variable.
- **It does not protect against someone who can rewrite the vault.** A snapshot, its hash file and the manifest entry can all be edited together. Use version control, review and CI permissions for that.
- **It does not cover every file.** `mode.json` and `mode_auth.json` are not covered by the hash check.
- **It does not check the merged schema the engine loads.** The Go engine verifies the vault, then reads the merged schema from `.chameleon/state/schema.merged.cham` (or the path in `schema.merged_output`) without comparing it with the current version hash. `chameleon verify` does report whether that file matches, but the engine does not enforce it at startup.
- **It does not set filesystem permissions.** Directories are created `0755` and files `0644`; only `mode_auth.json` is `0600`.

These are known gaps. Closing them is tracked in the project roadmap.

## Best practices

1. Do not edit vault files by hand. Use the CLI.
2. Commit `manifest.json`, `versions/`, `hashes/` and `integrity.log` if you want a shared history. Keep `mode_auth.json` out of version control.
3. Set a mode password after the first migration.
4. Run `chameleon verify` in CI.
5. Review changes to `.chameleon/vault/` in code review like any other source change.

## Commands

```bash
chameleon migrate --dry-run      # creates the vault on first use
chameleon verify                 # integrity check (exit 0 = ok)
chameleon status                 # version, integrity and mode
chameleon journal schema         # version history
cat .chameleon/vault/integrity.log
```
