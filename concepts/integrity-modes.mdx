---
title: Integrity Modes
description: A local gate on schema-changing commands, with password-protected upgrades
---

Integrity Modes are a **local safeguard** on the commands that change your schema or generate one from a database. A mode is stored in the Schema Vault; moving to a less restrictive mode asks for a password.

<Warning>
  Be clear about what this is. It protects against accidents and casual changes made through the `chameleon` CLI. It is **not** an access-control system: the mode and the password verifier are plain files in `.chameleon/vault/`, and anyone who can write to that directory can change them. Real authority over your database comes from PostgreSQL roles and from who can run the CLI in CI, not from this feature.
</Warning>

## The four modes

| Mode | Ring (naming only) | Default | What it enforces today |
|------|--------------------|---------|------------------------|
| `readonly` | R3 | yes | `migrate` and `introspect` stop once a schema version exists |
| `standard` | R2 | no | `migrate` and `introspect` allowed |
| `privileged` | R1 | no | Same as `standard`, and allows `config set schema-paths` |
| `emergency` | R0 | no | Same as `privileged`, with an extra typed confirmation for `schema-paths` |

`readonly` is the only mode that changes what `migrate` and `introspect` do. `standard`, `privileged` and `emergency` differ today only in which `config` operations they allow. The names describe intent, but there is no reduced validation in `privileged` and no disabled integrity checking in `emergency`: both still run the vault integrity check on `migrate`.

<Note>
  The "ring" labels are a naming convention borrowed from Unix. They do not imply kernel-style isolation.
</Note>

## Lifecycle

1. `chameleon init` does not create the vault, so there is no mode yet.
2. The first `chameleon migrate` creates the vault. The mode starts as `readonly`.
3. The first migration itself is **not** blocked, because no version existed when it started. From then on, `migrate` and `introspect` are blocked.

```bash
chameleon migrate --apply        # first run: creates the vault, applies
chameleon migrate --apply        # later runs in readonly:
# Read Only Paranoid Mode is active - schema modifications are blocked
# Error: readonly mode: schema locked
```

To make changes, set a password and upgrade:

```bash
chameleon config auth set-password        # minimum 8 characters
chameleon config set mode=standard        # asks for the password
chameleon migrate --apply
chameleon config set mode=readonly        # downgrade: no password
```

Without a password, an upgrade fails with `mode password not configured`, so a vault without a password stays in `readonly` through the CLI.

<Warning>
  `migrate` is currently create-only: existing tables are not altered. Read [`chameleon migrate`](/cli/migrate) before relying on it.
</Warning>

## Passwords

- The password is required to move to a **less** restrictive mode (`readonly` to `standard`, and so on). Moving to a more restrictive mode does not need one.
- It is stored as a salted SHA-256 hash in `.chameleon/vault/mode_auth.json` (file mode `0600`). A single round of SHA-256 is fast to brute-force if the file leaks, so use a long, unique password.
- For CI, set `CHAMELEON_MODE_PASSWORD` instead of typing it.
- The default `.chameleon/.gitignore` does not ignore `vault/`. Add `.chameleon/vault/mode_auth.json` to your own `.gitignore` so the verifier is not committed.

## Where the mode lives

| File | Contents |
|------|----------|
| `.chameleon/vault/mode.json` | The current mode (source of truth) |
| `.chameleon/vault/mode_auth.json` | Salt and hash of the password |
| `.chameleon/vault/manifest.json` | A legacy copy of the mode, for compatibility |

`mode.json` is not covered by the vault's hash verification. Editing it by hand changes the mode without a password and without an audit entry. That is why this is a safeguard and not a control.

## Checking the mode

```bash
chameleon config get mode
chameleon status
```

## What is recorded

Mode changes and denied attempts are written to the journal and to `.chameleon/vault/integrity.log`:

```
2026-11-03T10:30:00Z [MODE] action=mode_updated mode=standard
2026-11-03T10:31:12Z [MODE] action=mode_change_denied mode=standard reason=invalid_mode_password
```

Both files are plain, append-by-convention logs. Nothing prevents someone with file access from editing them, so treat them as an operational record rather than as tamper-proof evidence.

## Best practices

1. Set a mode password as soon as the vault exists.
2. Keep `readonly` as the resting state, and upgrade only for the migration.
3. Keep `mode_auth.json` out of version control.
4. In CI, pass the password through your secret store and `CHAMELEON_MODE_PASSWORD`.
5. Enforce who may change schemas with your CI permissions and PostgreSQL roles; use modes as a second, local check.

## Planned

Making mode enforcement tamper-evident, and making `privileged` and `emergency` behave differently from `standard`, is on the roadmap. Until then, rely on the table above.
