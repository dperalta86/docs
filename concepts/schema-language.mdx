ChameleonDB has a small **domain-specific language** for describing a data model: entities, fields, relations, constraints and defaults. Schemas live in `.cham` files, are parsed and type-checked by the Rust core, and are used to validate queries and generate PostgreSQL DDL.

## Overview

With the schema language you can:

- Define entities, fields and relations
- Set types, constraints and defaults
- Attach backend annotations (metadata only, for now)
- Have the schema checked before anything runs

<Info>
  A schema is parsed and type-checked before any SQL is generated. Syntax errors, unknown relation targets, missing primary keys and the other checks listed below are reported at that point, not at query time.
</Info>

## Basic syntax

### Entities and fields

```chameleon
entity User {
    id: uuid primary,
    email: string unique,
    name: string,
    created_at: timestamp default now(),
}
```

A field is `name: type`, followed by optional modifiers, and ends with a comma. Comments use `//`.

## Types

| Type | PostgreSQL | Notes |
|------|-----------|-------|
| `uuid` | `UUID` | |
| `string` | `VARCHAR` | |
| `int` | `INTEGER` | |
| `float` | `DOUBLE PRECISION` | |
| `decimal` | `NUMERIC` | |
| `bool` | `BOOLEAN` | |
| `timestamp` | `TIMESTAMP` | |
| `vector(N)` | `VECTOR(N)` | Dimension `N`; requires the pgvector extension in PostgreSQL |
| `[type]` | `type[]` | For example `[string]` becomes `VARCHAR[]` |

There are no separate `date` or `time` types. Use `timestamp`.

### Nullable fields

Fields are `NOT NULL` unless you add the `nullable` modifier:

```chameleon
entity User {
    id: uuid primary,
    name: string,               // NOT NULL
    middle_name: string nullable,
}
```

<Warning>
  The `string?` shorthand is not supported and fails to parse.
</Warning>

## Constraints

### Primary key

Every entity must have exactly one primary key:

```chameleon
id: uuid primary,
```

An entity without one is rejected: `Entity 'Post' has no primary key`.

### Unique

```chameleon
email: string unique,
```

## Default values

```chameleon
entity User {
    id: uuid primary default uuid(),
    created_at: timestamp default now(),
    status: string default "active",
    is_verified: bool default false,
    login_count: int default 0,
}
```

Supported defaults:

- `now()` - Current timestamp
- `uuid()` or `uuid_v4()` - Random UUID, generated by PostgreSQL (`gen_random_uuid()`)
- Literals: strings, booleans, integers and floats

The default must match the field type; the type checker rejects mismatches.

## Relations

Relations are declared inside an entity, next to the fields. There are two forms.

### Has-many: `[Target] via foreign_key`

```chameleon
entity User {
    id: uuid primary,
    posts: [Post] via author_id,
}

entity Post {
    id: uuid primary,
    author_id: uuid,
    author: User,
}
```

`via` names the field in the target entity that holds the foreign key, and that field must exist. A has-many without `via` is rejected.

### Belongs-to: `Target`

A relation to a single entity, as `author: User` above. The foreign key field (`author_id`) is a normal field you declare yourself.

### Foreign keys in the generated SQL

Foreign key constraints are generated from has-many relations (`FOREIGN KEY (author_id) REFERENCES users(id)`). A belongs-to relation on its own does not generate a constraint.

<Note>
  A one-to-one shape can be modeled with a belongs-to relation plus a `unique` foreign key field. There is no dedicated one-to-one syntax.
</Note>

## Annotations

Backend annotations are hints attached to a field:

```chameleon
entity User {
    id: uuid primary,
    session_token: string @cache,
    monthly_spent: decimal @olap,
    embedding: vector(384) @vector,
}
```

| Annotation | Intended use |
|-----------|--------------|
| `@cache` | Cache-friendly data |
| `@olap` | Analytical queries |
| `@vector` | Vector search; only valid on `vector(N)` fields |
| `@ml` | Machine-learning features |

<Info>
  Annotations are validated and carried in the schema, but they do not change the generated SQL or route to other backends today. ChameleonDB targets PostgreSQL only.
</Info>

## Complete example

```chameleon
entity User {
    id: uuid primary default uuid(),
    email: string unique,
    name: string,
    created_at: timestamp default now(),
    posts: [Post] via author_id,
    orders: [Order] via user_id,
}

entity Post {
    id: uuid primary default uuid(),
    title: string,
    content: string,
    published: bool default false,
    author_id: uuid,
    author: User,
    created_at: timestamp default now(),
}

entity Order {
    id: uuid primary default uuid(),
    total: decimal,
    status: string default "pending",
    user_id: uuid,
    user: User,
    items: [OrderItem] via order_id,
}

entity OrderItem {
    id: uuid primary default uuid(),
    order_id: uuid,
    product_name: string,
    quantity: int,
    price: decimal,
    order: Order,
}
```

## Validation

Schemas go through two stages:

1. **Parser** (LALRPOP grammar) - Syntax, producing an AST
2. **Type checker** - Semantic rules

The type checker verifies that:

- Every entity has exactly one primary key
- Relation targets exist
- Has-many relations declare `via`, and the foreign key field exists
- Entity and field names are not duplicated
- Defaults match their field type
- `@vector` is only used on `vector(N)` fields, and backend annotations are not placed on primary or unique fields
- There are no circular dependencies between relations

### Error messages

Messages come from the Rust core. Parse errors include the line and column; type errors name the entity and the field.

```
Parse error at line 3, column 14: Invalid token

Entity 'Post' has no primary key

Entity 'Post' references unknown entity 'Usr' in relation 'author'
```

The checker does not suggest corrections ("did you mean...").

## Schema files

```bash
schema.cham                 # one file
schemas/                    # or several; they are merged
  ├── user.cham
  ├── post.cham
  └── order.cham
```

`chameleon migrate` loads every `.cham` file under `schema.paths` in `.chameleon.yml`, merges them and validates the result. `chameleon validate <file>` checks a single file in isolation, so a relation to an entity defined in another file is reported as unknown there.

## Using the CLI

```bash
chameleon validate schemas/user.cham   # one file
chameleon migrate --dry-run            # merged schema + generated SQL
chameleon migrate --apply              # register a version and apply
```

<Warning>
  `migrate` is currently create-only: it creates missing tables and leaves existing ones untouched. See [`chameleon migrate`](/cli/migrate).
</Warning>

## Schema evolution

Each schema change that you migrate registers a new version in the [Schema Vault](/concepts/schema-vault), with its hash and parent. Adding a field to `User` and running `migrate --apply` records `v002`.

Applying that change to an existing table (for example `ALTER TABLE ... ADD COLUMN`) is not done by ChameleonDB yet. The vault tracks the history of your schema; bringing an existing database in line with it is still manual.

## Best practices

1. Use clear entity names (`User`, `Post`), in PascalCase. Table names are derived as snake_case plurals (`OrderItem` becomes `order_items`).
2. Always define a primary key.
3. Declare foreign key fields explicitly and connect them with `via`.
4. Commit your `.cham` files to version control.
5. Annotate only when you want the metadata; it has no runtime effect yet.

## What the language is not

- Not a general-purpose programming language
- Not a query language (see the [Query Builder](/query-builder))
- Not SQL, though it generates SQL
