ChameleonDB is a **schema-first governance layer for PostgreSQL**: you describe your data model in a `.cham` schema, and ChameleonDB validates it, records its versions, generates SQL for it and checks your queries against it. This page describes how the pieces fit together and what each one does today.

## Layers

```
┌─────────────────────────────────────────────┐
│  Your application (Go)                      │
│  - Query builder, mutations, debug mode     │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│  Go runtime (chameleon)                     │
│  - Engine: loads the merged schema          │
│  - SQL execution through pgx                │
│  - Error mapping, IdentityMap               │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│  Rust core (chameleon-core), through FFI    │
│  - Parser, type checker                     │
│  - SQL, mutation and migration generators   │
└─────────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────────┐
│  PostgreSQL                                 │
└─────────────────────────────────────────────┘

Alongside, driven by the CLI:
  Schema Vault (.chameleon/vault/)  - versions, hashes, log, mode
```

<Info>
  PostgreSQL is the only supported database. Other backends are not implemented.
</Info>

## Components

### Rust core (`chameleon-core`)

- **Parser** - Turns `.cham` source into an AST with a LALRPOP grammar: entities, fields, relations, modifiers, defaults and annotations.
- **Type checker** - Validates the AST: primary keys, relation targets, foreign keys, annotations, defaults and circular dependencies.
- **SQL generation** - Builds parameterized queries. Values are bound as `$1..$n` and identifiers are validated against the schema and quoted.
- **Mutation generation** - Insert, update and delete statements built the same way.
- **Migration generation** - A create-only DDL script: one `CREATE TABLE IF NOT EXISTS` per entity, in dependency order. It never drops or alters.

### Go runtime (`chameleon`)

- **Engine** - The entry point for applications. `NewEngine()` requires an initialized vault, verifies its integrity and loads the merged schema from `.chameleon/state/schema.merged.cham` (or `schema.merged_output` in `.chameleon.yml`).
- **Query executor** - Sends the generated SQL and parameters to PostgreSQL through pgx.
- **Error mapping** - Maps PostgreSQL errors to ChameleonDB errors.
- **IdentityMap** - Deduplicates parent objects in memory when you use `.Include()`.
- **CLI** - `init`, `migrate`, `validate`, `check`, `verify`, `status`, `journal`, `config`, `introspect`, `query`, `version`, `uninstall`, plus local `dashboard` and `playground-sql` servers.

<Warning>
  `NewEngineForCLI()` is exported and skips the vault checks. It exists for the CLI and tests. Applications should use `NewEngine()`. The vault is a consistency check, not a barrier that prevents a Go program from loading a different schema.
</Warning>

### Schema Vault

Versioned snapshots of your merged schema, SHA-256 hashes per version, an operations log and the integrity mode. See [Schema Vault](/concepts/schema-vault).

```
.chameleon/vault/
├── manifest.json
├── mode.json
├── mode_auth.json
├── integrity.log
├── versions/
└── hashes/
```

### Integrity modes

A local gate on `migrate` and `introspect`, with password-protected upgrades. See [Integrity Modes](/concepts/integrity-modes).

| Mode | Enforced today |
|------|----------------|
| `readonly` (default) | `migrate` and `introspect` blocked once a version exists |
| `standard` | Allowed |
| `privileged` | Allowed; also allows changing `schema-paths` |
| `emergency` | As `privileged`, with an extra confirmation |

### FFI boundary

The Rust core is compiled as a library and called from Go through a C ABI (cgo). Schemas and results cross the boundary as JSON strings; strings allocated by Rust are released with `chameleon_free_string`.

On Windows the release archive includes `chameleon.dll`, which must stay next to `chameleon.exe`.

## Compilation and validation flow

![Compilation Flow](../diagrams/Compilation_Flow.png)

```
.cham files
    ↓
Merge (schema.paths) and validate
    ↓
Parser (LALRPOP) → AST
    ↓
Type checker
    ↓
JSON across the FFI boundary
    ↓
Go runtime
    ↓
Vault: register version (SHA-256, snapshot, manifest, log)
    ↓
Migration generation (create-only DDL)
    ↓
Execution on PostgreSQL
```

## What `migrate --apply` does

```
1. Load config; create the vault if missing (mode readonly)
2. Verify every registered version's hash
3. If a version exists and the mode is readonly: stop
4. Merge and validate the schema files
5. Compare with the current version by hash
6. Generate the create-only SQL
7. Register the new version in the vault
8. Execute the SQL on PostgreSQL
9. Record the result in the journal and integrity.log
```

## What the guarantees mean

These are the properties ChameleonDB aims to provide, and their limits.

| Property | Where it comes from | Limit |
|----------|--------------------|-------|
| Invalid schemas are rejected before SQL is generated | Parser and type checker | Checks the schema, not your live database |
| Queries are checked against the schema | Rust core | Only for queries built with the builder |
| Values never appear in SQL text | Bound parameters | Applies to queries and mutations generated by the core; table and column names are validated and quoted |
| Changes to recorded schema history are detected | SHA-256 per version | Detection, not prevention; hashes live next to the files they cover |
| Schema-changing commands can be locked | Integrity mode `readonly` | A local safeguard; the mode file is plain and editable |
| Migrations never drop data | Create-only generator | Existing tables are also not altered |

Security reports and the project's security model are described in `SECURITY.md` in the repository. The query-injection issue fixed in v1.1.0-alpha is documented in its published GitHub security advisory.

## Design decisions

### Why Rust for the core?

A strong type system for the parser, type checker and SQL generators, and no runtime overhead on the parsing path.

### Why Go for the runtime?

Simple deployment, a mature PostgreSQL driver (pgx) and good fit for the CLI and application integration.

### Why FFI?

Each language does the part it is best at, and the core can be reused by other bindings later. The cost is a build that needs both toolchains and a native library next to the binary.

### Why a vault?

To treat the schema as a versioned artifact with a recorded history, instead of a set of migration scripts with no relation to each other.

## Project structure

```
chameleondb/
├── chameleon-core/          # Rust core
│   ├── src/
│   │   ├── ast/             # Schema structures
│   │   ├── parser/          # LALRPOP grammar
│   │   ├── typechecker/     # Validation
│   │   ├── sql/             # Query SQL generation
│   │   ├── mutation/        # Mutation SQL generation
│   │   ├── migration/       # DDL generation
│   │   └── ffi/             # C ABI bridge
│   └── tests/
├── chameleon/               # Go runtime and CLI
│   ├── cmd/chameleon/       # CLI
│   ├── pkg/
│   │   ├── engine/          # Public API
│   │   └── vault/           # Schema Vault
│   └── internal/
│       ├── admin/           # Journal and state tracking
│       └── schema/          # Schema merge
├── examples/
└── docs/
```

## Status

| Component | Status |
|-----------|--------|
| Parser, type checker | Working |
| Query and mutation generation (parameterized) | Working |
| Create-only migrations | Working; existing tables are not altered |
| Schema Vault | Working; detects inconsistencies, does not prevent tampering |
| Integrity modes | Working as a local safeguard; only `readonly` changes behavior |
| Introspection | Working; produces a draft schema |
| Query builder, mutations, IdentityMap | Working |
| Applying changes to existing tables (schema diff) | Planned |
| Other databases | Not planned in the current alpha |

ChameleonDB is alpha software. The [roadmap](/introduction) describes what is next, without dates.
