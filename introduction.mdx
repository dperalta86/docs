# Welcome to ChameleonDB

ChameleonDB helps you keep a reliable relationship between the schema you declare, the changes you make to it, and the real state of your database. It treats the schema as a versioned, hash-checked artifact, records every change in a local audit trail, and lets you restrict who may change the schema through integrity modes.

It is not a database engine and not an ORM. Today it works with PostgreSQL only.

<Warning>
  **ChameleonDB is alpha.** Interfaces and file formats may change. Releases before v1.1.0-alpha contain a vulnerability in query and mutation generation that is fixed in v1.1.0-alpha. If you use an earlier release, upgrade. See the [security advisory](https://github.com/chameleon-db/chameleondb/security/advisories/GHSA-2r6g-424r-6xmr).
</Warning>

## The problem

Database systems enforce strong guarantees over data but often treat schema evolution informally:

- **Schema drift** can happen silently over time
- **Failed migrations** can leave databases in an unknown state
- **Authority** for schema changes is usually implicit, not enforced
- **Audit trails** are often external, incomplete, or missing

## What ChameleonDB does

<CardGroup cols={2}>
  <Card title="Schema Vault" icon="vault">
    Versioned, hash-checked storage of your schema. Each registered version is stored locally with a SHA-256 hash of its source text and a reference to its parent version.
  </Card>
  <Card title="Integrity Modes" icon="shield-halved">
    Four ring-inspired modes (`readonly`, `standard`, `privileged`, `emergency`) decide whether the CLI allows schema changes. Raising the mode asks for a password.
  </Card>
  <Card title="Audit Trail" icon="list-check">
    An append-only log records the events the tool performs, with timestamps and version references.
  </Card>
  <Card title="Schema Language" icon="file-code">
    Declare entities, fields and relations in `.cham` files; parse and type-check them before anything touches your database.
  </Card>
</CardGroup>

## Quick example

<Steps>
  <Step title="Define your schema">
    Declare entities in a `.cham` file:

    ```go schema.cham
    entity User {
        id: uuid primary,
        email: string unique,
        name: string,
        posts: [Post] via author_id,
    }

    entity Post {
        id: uuid primary,
        title: string,
        content: string,
        published: bool,
        author_id: uuid,
        author: User,
    }
    ```
  </Step>

  <Step title="Initialize, preview, apply">
    ```bash
    chameleon init                  # creates .chameleon/, .chameleon.yml and schemas/example.cham
    chameleon migrate --dry-run     # preview the SQL
    chameleon migrate --apply       # registers v001 in the vault and applies the migration
    ```

    New vaults start in `readonly` mode, which blocks schema changes. See the [Quick Start](/quickstart) for the full flow.
  </Step>

  <Step title="The vault tracks every registered version">
    ```bash
    .chameleon/vault/
    ├── manifest.json       # current version and history
    ├── mode.json           # current integrity mode
    ├── integrity.log       # append-only audit trail
    ├── versions/
    │   └── v001.json       # snapshot of each registered version
    └── hashes/
        └── v001.hash       # SHA-256 of each version
    ```
  </Step>
</Steps>

## What works today

- **Schema language and checker.** Parse and type-check `.cham` files.
- **Migration generation for PostgreSQL.** Preview the SQL with `--dry-run`, then apply it. See the warning above about how migrations behave today.
- **Schema Vault.** Local versions with SHA-256 hashes and parent references.
- **Integrity modes.** Four modes that control what the CLI allows.
- **Integrity verification and audit log.** The vault is checked before operations; events are appended to a log.
- **Introspection.** Generate a schema from an existing PostgreSQL database.
- **Go data-access layer.** A query and mutation builder with field selection, eager loading and write guards. It is a supporting component, and its scope is under review.

## What the guarantees mean

<Note>
  - The vault **detects** changes made to its files outside the tool. It does **not** protect against someone who can edit both the files and their hashes.
  - Integrity modes control what the **CLI** allows. They do not replace database permissions; a user with direct database access is not restricted by them.
  - The hash is computed over the schema source text, so formatting changes alter it. A canonical form is planned.
</Note>

## Key features

### Schema Vault

Every registered schema version is recorded with a hash and its parent:

```bash
chameleon journal schema         # version history
chameleon journal schema v001    # one version
chameleon verify                 # check the vault against its recorded hashes
```

### Integrity modes

| Mode | Ring | Intended use | Schema changes |
|------|------|--------------|----------------|
| `readonly` | R3 | Production (default) | Blocked |
| `standard` | R2 | Development teams | Allowed through the normal flow |
| `privileged` | R1 | DBAs | Allowed directly, logged |
| `emergency` | R0 | Incident recovery | Allowed with checks relaxed, audited |

```bash
chameleon config get mode
chameleon config set mode=standard    # upgrade: asks for the mode password
chameleon config set mode=readonly    # downgrade: no password
```

<Warning>
  The mode password is a local safeguard. Its storage is being reviewed, and it is not a substitute for database roles.
</Warning>

### Go data-access layer

A supporting component for querying and writing data from Go. Values are sent as bound parameters, and field names are validated against the schema.

```go
users, err := eng.Query("User").
    Select("id", "name", "email").
    Filter("age", "gt", 25).
    Include("posts").
    Execute(ctx)
```

Use `Debug()` to see the SQL and its parameters. The SQL text contains placeholders and the values are listed separately:

```go
result, err := eng.Query("User").
    Select("id", "name", "email").
    Filter("email", "like", "ana").
    Debug().
    Execute(ctx)

// [SQL]
// SELECT "id", "name", "email"
// FROM "users"
// WHERE "email" LIKE $1 ESCAPE '\'
//
// [PARAMS]
// $1 = String("%ana%")
```

An update or delete without a filter is rejected with a `SafetyError`. See [Mutations](/api/mutations).

### Roadmap

The roadmap is organised in horizons, ordered by priority and without dates. It is a plan, not a promise.

| Horizon | Focus | Status |
|---------|-------|--------|
| H0 | Trustworthy base: the code behaves predictably and its claims match reality | In progress |
| H1a | Observe and drift: canonical model, introspection, baseline snapshots, drift reports | Planned |
| H1b | Controlled change: risk-classified plans, gates, verification of control level | Planned |
| H2 | Multi-environment platform: additional adapters, integrations, collaboration | Exploring |
| H3 | Distributed and offline-first: compatibility between revisions, sync-engine integration | Exploring |

Follow the work in the [issues](https://github.com/chameleon-db/chameleondb/issues) and read the [product definition](https://github.com/chameleon-db/chameleondb/blob/main/docs/product-definition.md).
