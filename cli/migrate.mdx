## Synopsis

```bash
chameleon migrate [--check | --dry-run | --apply]
```

Load the schema files, register a new schema version in the Schema Vault, generate the SQL and optionally apply it.

## Description

`migrate` takes no arguments. It reads `.chameleon.yml`, loads and merges every `.cham` file from `schema.paths`, validates the result and generates one SQL script for the whole schema.

By default it only shows what would happen. Nothing touches the database unless you pass `--apply`.

### What the generated script does

For the schema as a whole, the script contains:

1. One CREATE TABLE IF NOT EXISTS "<table>" (...) per entity, in dependency order, with primary keys, unique constraints, defaults and foreign keys.
2. Columns are ordered primary key first, then alphabetically; the output is deterministic.

There is no diff against the live database. The script is the same whether the tables exist or not, and whether the schema changed by one field or by fifty.

### Steps

1. Load the configuration and open the journal
2. Initialize the Schema Vault if `.chameleon/vault/` does not exist
3. Verify vault integrity. If it fails, the migration is aborted
4. If a version is already registered and the mode is `readonly`, stop (see [Integrity modes](#integrity-modes))
5. Load, merge and validate all schema files
6. Compare the merged schema with the current vault version
7. Generate and print the SQL
8. With `--apply`: register the new version, connect to PostgreSQL, run the script

## Flags

<ParamField path="--check" type="boolean" default="true">
  Show pending changes and the SQL. This is the default when no flag is given.
</ParamField>

<ParamField path="--dry-run" type="boolean" default="false">
  Print the SQL without applying it. Behaves the same as `--check`.
</ParamField>

<ParamField path="--apply" type="boolean" default="false">
  Execute the migration against the database in `DATABASE_URL` (or the connection string in `.chameleon.yml`).
</ParamField>

<Note>
  `--dry-run` still loads the vault, validates and writes the merged schema to `.chameleon/state/schema.merged.cham`, and creates the vault on first use. It does not register a version and does not connect to the database.
</Note>

export DATABASE_URL="postgresql://user:password@localhost:5432/dbname"
chameleon migrate --apply

### Retry of a version that was not applied

The version is registered in the vault before the SQL runs. If the connection or the execution fails, the version stays registered and the migration is recorded as `failed`. Running `chameleon migrate --apply` again, without changing the schema, detects this and retries:

```
⚠ Schema unchanged, but latest version v002 is not applied to database
```

## Integrity modes

The vault records an integrity mode (see [`chameleon config`](/cli/config)).

- The **first** migration is not blocked: the vault does not exist yet, so there is no mode to enforce.
- Once a version is registered and the mode is `readonly` (the default), `migrate` stops, including `--dry-run`:

```
✗ Read Only Paranoid Mode is active - schema modifications are blocked
...
Error: readonly mode: schema locked
```

To continue, set a mode password and upgrade the mode:

```bash
chameleon config auth set-password
chameleon config set mode=standard
```

<Note>
  The mode is a local safeguard, stored in files inside `.chameleon/vault/`. It protects against accidents and casual changes. It is not an access-control system: anyone who can write to that directory can change it.
</Note>

## Integrity failure

If the stored hashes do not match the vault files, `migrate` aborts before it reads your schema:

```
✗ INTEGRITY VIOLATION DETECTED
...
Recovery options:
   1. Run 'chameleon verify' for details
   2. Check .chameleon/vault/integrity.log
   3. Contact your DBA

✗ Migration aborted for safety
```

## Backups

`backup_on_migrate`1 is not implemented; with it enabled migrate --apply prints backup_on_migrate is not implemented yet: no backup was created. The script is create-only, but take your own backup before applying.

## Limits and behavior to know

- **Whole-schema script** - Every entity is included; existing tables are skipped.
- **Single statement batch** - The script runs as one `Exec`. Partial failure behavior depends on PostgreSQL; do not assume it is wrapped in a transaction.
- **Timeouts** - 30 seconds for the whole command and 10 seconds to connect.
- **Connection** - TLS is not enforced by ChameleonDB. For remote databases, set `sslmode` explicitly in your connection string and verify that it is honored.
- **Author** - The version records the `USER` environment variable (`unknown` if unset).
- **Rollback** - Not implemented, despite the `rollback` key in the generated config.
- **Schema errors** - If parsing fails, the merged schema is saved under `.chameleon/state/debug/` with a timestamp, and the error is mapped back to the original file and line when possible.

## Troubleshooting

### `readonly mode: schema locked`

See [Integrity modes](#integrity-modes).

### `failed to connect to database`

Check `DATABASE_URL`, that PostgreSQL is reachable and that the user can create and drop tables. The failed attempt is recorded in the journal:

```bash
chameleon journal migrations
chameleon journal errors
```

### `schema validation failed` / `failed to parse merged schemas`

Fix the schema and retry. To check a single file in isolation, use [`chameleon validate <file>`](/cli/validate).
