## Synopsis

```bash
chameleon config <subcommand> [args]
```

Read and change local ChameleonDB settings that live in the Schema Vault.

## Description

`config` manages three things:

- **Integrity mode** - A local setting that gates `migrate` and `introspect`
- **Mode password** - Required to move to a less restrictive mode
- **Schema paths** - Where `.cham` files are loaded from

<Warning>
  Every subcommand needs an initialized vault. A new project has none until you run `chameleon migrate` once, so `config` fails with `vault not initialized. Run 'chameleon migrate' first` before that.
</Warning>

## Supported keys

Only two keys exist:

| Key | `get` | `set` |
|-----|-------|-------|
| `mode` | yes | yes |
| `schema-paths` | yes | yes (requires `privileged` or `emergency`) |

Any other key fails with `unsupported key ... (supported: mode, schema-paths)`. Keys such as `database.driver` or `features.*` are edited in `.chameleon.yml` by hand.

```bash
chameleon config get schema-paths
```

```

```

Multiple paths are printed comma-separated.

## config set

```bash
chameleon config set <key>=<value>
```

### Mode

```bash
chameleon config set mode=standard
```

```
Enter mode password (or set CHAMELEON_MODE_PASSWORD env var): ********
✓ Paranoid Mode updated: standard
```

Valid values: `readonly`, `standard`, `privileged`, `emergency`. `admin` is accepted as an alias of `privileged`.

Moving to a **less restrictive** mode asks for the mode password. Moving to a more restrictive one does not:

```bash
chameleon config set mode=readonly
```

```
✓ Paranoid Mode updated: readonly
```

Denied attempts (no password configured, wrong password) are written to the journal and to the vault's `integrity.log`.

### Schema paths

```bash
chameleon config set schema-paths=schemas/,legacy/schemas/
```

Changing where schemas are loaded from can change what gets applied to your database, so it is gated:

- Requires `privileged` or `emergency` mode
- Each path must exist and must not be a symlink
- Asks for confirmation (`Continue? [y/N]`); in `emergency` mode you must type `I understand the risks`
- The change is recorded in `integrity.log`

## config auth set-password

```bash
chameleon config auth set-password
```

Set the mode password, or replace it. The minimum length is 8 characters.

```
Choose mode password (min 8 chars): ********
✓ Mode password configured
```

For non-interactive use, set `CHAMELEON_MODE_PASSWORD` instead of typing it.

### Where it is stored

The password is not stored in plain text. A salted SHA-256 hash is written to:

```
.chameleon/vault/mode_auth.json
```

<Warning>
  A single round of SHA-256 is fast to brute-force if the file leaks, and the file lives in the working tree. `.chameleon/.gitignore` ignores `vault/mode_auth.json` (`init` creates the rule and `config auth set-password` adds it to older projects), so it is not committed. A file that was committed before stays tracked: run `git rm --cached .chameleon/vault/mode_auth.json`. Use a long, unique password.
</Warning>

The rest of `vault/` (manifest, versions, hashes, integrity log) stays versioned. Because the verifier is not in the repository, each clone sets its own mode password.

## Integrity modes

| Mode | Enforced today |
|------|----------------|
| `readonly` (default) | `migrate` and `introspect` are blocked once a schema version exists |
| `standard` | `migrate` and `introspect` allowed |
| `privileged` | As `standard`, and allows `config set schema-paths` |
| `emergency` | As `privileged`, with an extra confirmation for `schema-paths` |

Be precise about what this means. `readonly` is the only mode that changes the behavior of `migrate` and `introspect`; `standard`, `privileged` and `emergency` currently differ only in which `config` operations they allow. The "reduced validation" or "no integrity checks" behaviors that the names suggest are not implemented.

The mode is a local safeguard against accidents and casual changes. It is not an access-control system: the files that hold it are writable by anyone with access to the project directory.

## Workflow

```bash
# 1. First migration creates the vault (new vaults start in readonly)
chameleon migrate --apply        # review --dry-run first

# 2. Set a password
chameleon config auth set-password

# 3. Allow changes
chameleon config set mode=standard

# 4. Apply further migrations
chameleon migrate --apply

# 5. Lock again
chameleon config set mode=readonly
```

## Configuration file

Everything else is configured in `.chameleon.yml`:

```yaml
database:
  driver: postgresql
  connection_string: ${DATABASE_URL}

schema:
  paths:
    - ./schemas
  merged_output: .chameleon/state/schema.merged.cham

features:
  auto_migration: true
  rollback: true
  backup_on_migrate: true
  audit_logging: true

safety:
  validation: true
  confirmation: false
```

<Note>
  Not every key has behavior behind it yet. For example, `backup_on_migrate` only prints a message and `rollback` is not implemented. The mode password hash is **not** stored here.
</Note>

## Troubleshooting

### `invalid mode password`

Re-enter it, or set `CHAMELEON_MODE_PASSWORD`. The attempt is logged.

### `mode password not configured`

```bash
chameleon config auth set-password
```

### Lost password

The password gate is local. If you lose the password and you own the project directory, remove `.chameleon/vault/mode_auth.json` and set a new one. Note that this is also why the mode is not a security boundary.

### Audit mode changes

```bash
chameleon journal last 50
```
